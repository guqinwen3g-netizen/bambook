## 任务书 S-BE-W3-1：DR-016 合票建模（订单↔出运多对多）

### 1. 现状与缺口（审计接地）

| 项 | 现状 | DR-016 要求 |
|---|---|---|
| 订单↔出运关系 | `Shipment.orderId` 单值标量（schema.prisma:2390），`ShipmentLine.orderLineId` 行级关联已存在但无一等公民分配记录 | 多对多：一单拆多票 + 一票合多单；每个订单参与某票出运须有**独立分配记录** |
| 带出逻辑 | `shipmentPackingService.pullLinesFromOrder` 仅支持单从带出 | 多单带出 + 分配记录同步生成 |
| 数量上限 | 仅箱内分配 ≤ 行数量（同票内） | **跨票**累计实际出运量 ≤ 订单可出运量 |
| 合票边界 | 无校验 | 仅同业务线 + 同一签约客户允许合票；面料与服装不得合票 |
| 交易方 | 仅 `customerRelationId`(billTo) + `carrierRelationId`(shipsVia) | 每票四方：收货方/目的工厂、单证收件方、开票对象、实际付款方，均须正式关联方档案（snapshot FK，禁自由文本） |
| 门禁 | 出运资格按票整体判定 | 按**每个来源订单分配**逐项核验 QC/S/S/RC/客户确认；合票不得以一票已放行掩盖另一票未满足门禁 |
| 状态回写 | Shipment→Order 状态联动已有（orderLinkService） | 订单全部应出数量完成才进入完整出运；部分出运可见剩余数量/后续计划/分批履约状态 |

### 2. Schema 设计（新模型 + 字段扩展）

**新模型 `ShipmentOrderAllocation`**（出运分配记录，id 格式 `SHPA__${shortId}`，遵循 snapshot FK 范式不加 @relation）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String @id | `SHPA__${shortId}` |
| shipmentId | String | 所属票（snapshot FK，@@index） |
| orderId | String | 来源订单（snapshot FK，@@index） |
| orderLineId | String? | 来源订单行（行级分配时填；订单级整单分配为 null） |
| plannedQty | Decimal? @db.Decimal(18,4) | 计划出运数量 |
| actualQty | Decimal? @db.Decimal(18,4) | 实际出运数量（发货确认后回填） |
| unit | String? | 单位快照（m/yd/kg/pcs） |
| batchOrCartonNote | String? | 批次/箱号备注（如适用，DR-016 原文"如适用"） |
| status | String | `Planned` \| `PartiallyShipped` \| `Fulfilled` \| `ShortShipped`(短装) \| `Cancelled` |
| exception | String? | 异常说明（短装/溢装原因） |
| createdAt / updatedAt | BigInt | 时间戳 |

约束：`@@unique([shipmentId, orderId, orderLineId])`（同票同订单行不重复分配）；无软删（随 Shipment 过滤）。

**Shipment 扩展四方交易方**（均 snapshot FK → Relation，可空，逐步迁移）：

| 字段 | 语义 |
|---|---|
| consigneeRelationId / consigneeName | 收货方/目的工厂 |
| docRecipientRelationId / docRecipientName | 单证收件方 |
| payerRelationId / payerName | 实际付款方 |
| （既有 `customerRelationId` 保持 = 开票对象 billTo，不重命名，注释更新明确语义） |

### 3. 服务层规则（fail-closed）

1. **合票校验** `assertConsolidationAllowed(tx, shipmentId)`：票内全部分配的来源订单 → 同一 `customerId`（签约客户）且同一 `businessLine`；任一不符抛 `CONSOLIDATION_CUSTOMER_MISMATCH` / `CONSOLIDATION_BUSINESS_LINE_MISMATCH`（409）。面料单与服装单天然由 businessLine 校验拦截。
2. **跨票累计上限**：新增/修改分配时 `SUM(actualQty) OVER (该 orderLine 全部分配, 排除已取消票) + 本次 ≤ OrderLine.quantity`，超限抛 `ORDER_LINE_OVER_ALLOCATED`（409）；整单分配按订单行汇总同规则。
3. **逐分配门禁**：出运资格判定从"按票"升级为"按分配循环"——`checkShipmentEligibility` 对票内每个来源订单分别跑 bulkQc/SS/RC 三条件（服装单 applicable=false 跳过对应链），任一订单不合格则整票 `eligible=false` 并在阻断明细中列出**逐订单**的缺失项（证据字段按订单分组）。
4. **状态回写**：分配 actualQty 变动后重算来源订单出运进度：全部行 Fulfilled → 订单可进 `Delivered` 链；部分 → 订单详情暴露剩余数量/后续计划（查询投影，不落冗余字段）。
5. **兼容性**：`Shipment.orderId` 保留为"主订单"投影（= 票内第一条分配的 orderId），既有读路径不破坏；新写路径只写分配表，orderId 由服务层派生维护。

### 4. 迁移（三步法）

1. 加 `ShipmentOrderAllocation` 表 + Shipment 三个新四方字段（全部可空）
2. 回填：现存 `Shipment.orderId IS NOT NULL` 的行 → 每票生成一条订单级分配（orderLineId=null，plannedQty=票内行 quantity 合计，status 按 Shipment.status 映射：Draft/Booked→Planned；Shipped..Cleared→Fulfilled 且 actualQty=plannedQty；Cancelled→Cancelled）
3. 验证脚本：回填行数 = `SELECT count(*) FROM Shipment WHERE orderId IS NOT NULL AND deletedAt IS NULL`

### 5. API 与测试

- 路由扩展：`POST/DELETE /api/v1/shipping/:id/allocations`、`PATCH /api/v1/shipping/:id/allocations/:allocId`（写全部走 JWT + scope + routeAudit）；`pullLinesFromOrder` 升级支持 `orderIds: string[]`
- 测试（≥12 用例）：同客户同业务线合票通过 / 跨客户拒绝 / 跨业务线拒绝 / 面料服装混合拒绝 / 跨票累计超限拒绝 / 取消票不计入累计 / 逐分配门禁（A 单 SS 未确认整票 blocked 且明细按订单分组）/ 状态回写部分履约 / 回填幂等 / orderId 投影一致 / 分配唯一约束 / DR-013 例外放行后分配仍逐项记录

### 6. 边界划分

- **S-BE 交付**：schema + 迁移 + 服务 + 路由 + 测试（W3）
- **S-FE 后续接入**（W4 另行发令，不在本任务书）：出运编辑器多单选择器、装箱明细按订单分组、订单详情页分批履约进度条
- **禁止**：本任务不含 UI；不改 `App.tsx`；不删除 `Shipment.orderId`（降级为投影）
