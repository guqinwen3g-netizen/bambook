# 订单管理改为“面料项目”为主的设计

日期：2026-05-09

## 背景

现在订单管理页面本质上还是把一个 PO 当成一个订单主体。列表里虽然可以把同一个 PO 展开成多行，但点击任意一行进入详情时，打开的还是 PO 级详情，所以多块面料的 PO 会出现一个严重问题：点第二块、第三块面料，看到的仍然是这个 PO 或第一块面料的信息。

真实业务不是这样：

- 一个 PO 可以包含多块面料 / 多个产品项目。
- 跟单员实际跟进的是某一块面料，而不是只跟进整个 PO。
- PDF 导入仍然应该一次导入一个完整 PO，但入库后要拆成一个 PO 抬头 + 多个面料项目。
- 手动录入时，应该一次新增一个面料项目。PO 号只是这个面料项目的一个归属字段。

## 核心决定

订单管理页面以后以 `OrderLine` 作为主对象。

也就是说：

- `Order` 保留为 PO 抬头 / 容器。
- `OrderLine` 表示 PO 下面的一块面料 / 一个产品项目。
- 表格每一行、详情页、状态跟进、手动新增，都围绕 `OrderLine` 来做。

## 数据模型

### PO 抬头：`Order`

`Order` 只放整个 PO 共享的信息，例如：

- PO 号
- 客户
- 客户代码
- PO 日期
- 季节
- 币种
- 交付条款 / 付款条款
- 联系人和电话
- 收货方 / ship-to 信息
- 结款方信息，如果它是整个 PO 共享的
- PDF 导入来源、导入时间等元数据

`Order` 不再作为订单管理表格里的主行身份。

### 面料项目：`OrderLine`

`OrderLine` 表示一块具体面料，要放这块面料自己的信息，例如：

- 系统内部 line id
- 所属 PO 的 `orderId`
- 行序号 `lineNumber`
- PO item 编号 `itemNo`
- 客户物料号 / 客供品号
- 工厂品色号
- 描述 / 颜色
- 成分
- 门幅
- 克重
- 数量
- 单位
- 单价
- 小计
- 出厂日期
- 到港日期
- 状态
- 跟单员后续补充的、只属于这一块面料的信息

状态必须是面料项目级别。一个 PO 里可以同时有：

- `0010` 生产中
- `0020` 待生产
- `0030` 已出运

## PO Item 编号规则

`itemNo` 是业务编号，不是数据库主键。

手动新增时，系统默认按四位编号递增：

- 第一块面料：`0010`
- 第二块面料：`0020`
- 第三块面料：`0030`

用户可以手动修改 `itemNo`。

第四位可以表示修改版。例如：

- 原本是 `0010`
- 后来可以改成 `0011`
- 但这不影响第二块面料仍然是 `0020`

所以系统自动生成下一个编号时，不能简单地拿最大数字加 10，而是要识别主序号。比如：

- 已有：`0010`、`0011`
- 下一个默认编号应该是：`0020`

PDF 导入时，如果客户 PDF 里本来有 item 编号，例如 Peerless 现在解析出来可能是 `00010`，系统要保留这个原始编号。  
但订单管理页面展示时，按我们约定的四位业务编号展示，比如显示成 `0010`。手动新增默认也使用四位编号。

## 表格行为

订单管理表格的每一行都代表一个面料项目，而不是一个 PO。

每行显示一个 `OrderLine`，同时带上它所属 PO 的共享信息。

建议主编号显示为：

```text
PO 4500159423 / 0010
PO 4500159423 / 0020
```

点击某一行时，选中的必须是这一行对应的面料项目，而不是只选中它所属的 PO。

状态光点读取 `OrderLine.status`。  
如果该面料项目已完成 / 已收到货款，则不显示光点，但仍保留光点空位，保证表格视觉对齐。

## 详情页行为

详情页打开的是某一个面料项目。

详情页顶部应该显示这个面料项目的关键信息：

- PO 号 / item 编号
- 当前状态
- 数量
- 金额
- 出厂日期
- 客户

详情页内容分成两类：

- PO 抬头信息：作为共享上下文展示，必要时可以编辑。
- 面料项目信息：作为主要编辑区域。

编辑只属于单块面料的字段时，要更新 `OrderLine`。  
编辑整个 PO 共享的字段时，才更新父级 `Order`，并影响同一个 PO 下的所有面料项目。

## PDF 导入流程

PDF 导入仍然按 PO 进行：

1. 一个 PDF 解析成一个 `ParsedOrder`。
2. 入库时创建 / 更新一个 `Order` 抬头。
3. 把 PDF 里的每一行保存成一个 `OrderLine`。
4. 如果 PDF 行里有 item 编号，就保留 PDF 的编号。
5. 如果 PDF 行里没有 item 编号，就自动生成 `0010`、`0020`、`0030`。

重新导入同一个 PO 时，要保护用户已经手动补充过的面料项目信息。  
不能像现在一样简单删除所有 lines 再重建，因为以后 line 上会有状态、跟单补充、出运、收款等信息，删掉重建会丢数据。

重新导入时应该按稳定身份更新 line：

- 优先用 `orderId + itemNo` 匹配同一条面料项目。
- 如果没有 itemNo，才考虑用行位置作为兜底。

## 手动新增流程

手动新增的对象是“面料项目”。

表单需要包含：

- PO 号
- item 编号
- 创建或更新 PO 抬头所需的客户、日期、季节等字段
- 这块面料自己的字段
- 这块面料的状态

保存逻辑：

- 如果 PO 不存在：先创建 PO 抬头，再创建第一条面料项目。
- 如果 PO 已存在：复用已有 PO 抬头，只新增一条面料项目。
- item 编号默认根据同一个 PO 下已有面料项目生成。
- 用户可以在保存前修改 item 编号。

按钮文案要从“录入新订单”改成“新增面料项目”或类似表达。

## API 设计

保留现有订单接口，避免一次性破坏已有功能，同时增加以 line 为主的新接口：

- `GET /api/v1/orders` 可以继续返回 PO，并包含 `lines`。
- 新增 `GET /api/v1/order-lines`，给订单管理表格直接读取面料项目列表。
- 新增 `POST /api/v1/order-lines`，用于手动新增面料项目。
- 新增 `PUT /api/v1/order-lines/:id`，用于编辑某个面料项目。
- 现有 `POST /api/v1/orders/import` 继续接收 PDF 解析结果，但持久化逻辑要改成 line 级 upsert，不能粗暴删掉重建。

前端短期可以先从 `GET /orders` 里的 `lines` 组装表格；长期应该使用 `GET /order-lines` 这种更清晰的 line-first 接口。

## 迁移策略

为了不把现有数据弄乱，分阶段改：

1. 给 `OrderLine` 增加状态和必要的跟单字段。
2. 把现在错误挂在 `Order` 上、但其实属于单块面料的字段，补到已有 `OrderLine` 上。
3. 对没有 lines 的老订单，自动创建一条默认 line，避免数据消失。
4. 暂时保留 `Order` 上的旧字段，保证兼容。
5. 把 UI 改成按面料项目选择、查看和编辑。
6. 稳定后，再逐步减少对 `Order` 上那些旧面料字段的依赖。

## 测试范围

需要覆盖这些情况：

- 一个多行 PDF 导入后，生成一个 PO 抬头和多条面料项目。
- 点击第二条面料项目，打开的是第二条详情，不是第一条。
- 手动新增一个不存在的 PO 时，会创建 PO 抬头和一条面料项目。
- 手动新增一个已有 PO 时，只新增一条面料项目。
- 默认 item 编号能生成 `0010`、`0020`、`0030`。
- 已有 `0010` 和 `0011` 时，下一个默认编号是 `0020`。
- PDF 里带来的 item 编号会被保留。
- 表格状态光点由每条面料项目自己的状态决定。
- 重新导入 PDF 不会擦掉用户手动补过的 line 级字段。

## 实现备注

当前代码里已经有 `OrderLine`、`ParsedLine`、`Order.lines` 和 PDF 导入持久化逻辑。  
问题不是完全没有 line 模型，而是订单管理 UI、手动新增接口、详情页字段字典还在把 `Order` 当成主要编辑对象。

所以实现时应该升级现有 line 能力，而不是另起一套平行模型。
