### v2 修订（2026-08-19 代码级评审）

v1 设计经代码级评审（对照 `relationServiceV2.ts` 行级权限实现）发现 4 个设计缺陷，本版修复：

| # | v1 缺陷 | 后果 | v2 修复 |
|---|---------|------|---------|
| 1 | 团队归属缓存进 JWT claims（7 天 cookie） | 退组/解散后最长 7 天仍可见共享数据，违反即时失效（T-03） | **每请求解析**：按 `TeamMember.userId` 索引查询（毫秒级），可选 60s 进程内缓存（§5.2） |
| 2 | `TeamDataGrant.team` 外键 `onDelete: Cascade` | 物理删组会连带物理删授权行，审计链断裂 | 解散走**事务化软删**（先批量 revoke 再软删组）；AuditLog 为审计最终真源（§9.2） |
| 3 | entityType 起步三值（relation/order/quotation） | 订单可见性当前**无行级过滤**（Order 模型无 departmentId），直接共享订单语义悬空；且「看得到订单看不到客户」是畸形可见性 | 起步**只共享 Relation（客户/供应商档案）**，订单/报价/跟进作为子实体**派生可见**（§5.3） |
| 4 | 授权资格写成「本部门归属的数据」 | 归属判定口径不唯一（departmentId 可能缺） | 收敛为不变量：**对实体有行级写权限者才可共享该实体**（复用既有写权限校验，§6.1） |

## §2 概念定位：部门 vs 小组

| 维度 | 部门 Department | 小组 Team |
|------|---------------|-----------|
| 本质 | 行政组织架构（**目录**） | 业务分组单元（**数据视野驱动**） |
| 组建逻辑 | 稳定汇报线（业务部/质量部/财务部/后勤部/总经办） | 按品牌客户/市场/业务类型自由组建（如「波兰成衣组」「日本面料组」） |
| 成员规则 | 单一归属（`UserAccount.primaryDeptId` 一对一） | 多对多（一人可同时进 N 个组，TeamMember） |
| 跨部门 | 否，树形封闭 | 是，`Team.departmentId` 可空 = 天然跨部门（业务员+主管+老板+后勤混编同组） |
| 消费场景 | 组织架构树目录展示 / DR-007 审批人解析 / 汇报线（**v2.1 起退出数据视野计算**） | **数据视野唯一协作维度**：组内可见共享的客户档案与跟进 + 项目任务挂靠 |
| 生命周期 | 长期稳定（低频变更） | 高频（项目启动建组、结束解散） |
| 维护者 | 管理员（人事管理） | 销售主管/管理员（随业务调整，人事管理入口） |

**铁律**：小组**不参与**审批人解析（那是 DR-007 部门 `headId` 的职责）；小组**只影响数据可见性**。两条链路正交解耦，避免「一条数据到底跟部门走还是跟组走」的语义混乱。

**多组叠加的心理模型**：用户进 N 个组 ≠ 界面分成 N 块。类比微信：进了 10 个群，消息列表仍是同一条信息流，靠头像区分来源。UI 呈现见 §8。

## §3 建模取舍

### 3.1 方案 A：业务实体直接归属（挂 teamId）

在 Relation 上直接加 `teamId String?`。

| 优点 | 缺点 |
|------|------|
| 模型简单，查询快（单字段过滤） | **单值归属**：H&M 无法同时属于「欧洲市场组」+「H&M 品牌组」 |
| 无新增表 | 组解散时数据要迁移（脏活） |
| | 与部门归属并存，组织归属出现两个真源 |

### 3.2 方案 B：共享授权表（TeamDataGrant）✅ 采用

数据本体不动（归属仍是部门链路），新增授权表表达「这个实体共享给哪个组看」——**云文档分享模型**：文件不动、还在原主人手里，只把查看权限发给若干群。

| 优点 | 缺点 |
|------|------|
| 多对多：一个客户可同时授权多个组 | 多一张表，可见性查询 OR 子条件 |
| 数据本体不动：DR-007 审批链零污染 | 授权操作比勾字段多一步 |
| 组解散 = 撤销授权，数据无感回归部门范围 | |
| 授权自带审计链（谁/何时/撤销/理由） | |

### 3.3 方案 C：起步收敛——只共享 Relation，子实体派生（v2 新增，与 B 合并采用）

v1 允许分别共享 relation/order/quotation。评审否决：

1. **业务心智**：用户说「把 H&M 共享给欧洲组」，不会说「共享 H&M 档案但不共享其订单」——客户档案与其订单/报价/跟进天然一体，拆开共享是畸形可见性（看得到订单看不到客户）；
2. **现状依赖**：Order 模型无行级 scope 字段，订单维度授权无消费点；
3. **模型经济**：一张授权行解锁整棵子树，授权管理成本低一个量级。

**最终形态**：`entityType` 字段保留（为未来独立共享单张报价单等场景预留），但 Phase 2 仅消费 `'relation'`。子实体可见性由 §5.3 派生规则承接。

**明确不做**（防过度设计）：
- 不做组的自动规则归集（rule-based grant，如「欧洲客户自动进欧洲组」）——Phase 4 演进预留，首期手动授权；
- 不做组内层级（组长→副组长）；只保留 `Team.leaderId` 单一组长 + `TeamMember.role`（member/leader）既有字段；
- 不做跨租户/对外共享（供应商门户等）——纯内部协作场景。

## §4 数据模型设计

### 4.1 新增：TeamDataGrant（Prisma）

```prisma
/// DR-042 小组数据共享授权：业务实体 × 小组 多对多受控共享。
/// 铁律：数据本体组织归属不变（部门链路），本表仅表达「共享视图」。
model TeamDataGrant {
  id           String    @id @default(cuid())
  teamId       String
  entityType   String    // 起步仅 'relation'（§3.3）；字段保留扩展位
  entityId     String    // 被共享实体 id（快照引用，不强 FK——与 Order.customerRelationId 同范式）
  permission   String    @default("read+followup") // 'read'（纯只读）| 'read+followup'（可加跟进）
  grantedBy    String    // 授权人 UserAccount.id
  grantedAt    DateTime  @default(now())
  revokedAt    DateTime? // 软撤销（null=生效中）；保留行以留授权历史
  revokedBy    String?
  revokeReason String?

  team Team @relation(fields: [teamId], references: [id]) // 不设 Cascade（§0 修订 2）：物理删组由服务层禁止，解散走事务化软删

  @@unique([teamId, entityType, entityId]) // 幂等锚点：同实体对同组仅一行
  @@index([entityType, entityId])          // 反查：这条数据共享给了哪些组
  @@index([teamId, revokedAt])             // 正查：这个组生效中的授权
}
```

设计要点：
- **软撤销不物理删**：`revokedAt` 置位即失效；再授权 = 复活原行（revokedAt 置 null），`@@unique` 天然幂等，完整历史保留在行上 + AuditLog 双轨；
- **entityId 不强 FK**：与 `Order.customerRelationId` 快照引用同范式（Relation 可独立归档，不级联）；
- **permission 只有两档**：`read` / `read+followup`。**没有 write 档**——档案本体永远只有归属部门可写（§6.2），规避多人共改一条档案；
- **Team 关系不设 onDelete: Cascade**：v1 的 Cascade 是审计链断裂隐患（物理删组连带物理删授权行）。解散流程由服务层事务化处理（§9.2），物理删组被服务层禁止。

### 4.2 复用既有（零改动）

- `Team`（schema.prisma:1198）：`leaderId` 即组长；`departmentId` 可空保持跨部门语义；`deletedAt` 软删承载解散；
- `TeamMember`（schema.prisma:1219）：`role`（member/leader）+ `leftAt` 退出标记；
- `DataScopeRule`（rolePermissionMatrix.ts:304）：`{ kind: 'team' }` 分支启用语义变为「部门维 ∪ 小组维」合成（§5.1），双文件同步铁律照旧。

### 4.3 AuditLog 动作扩展

| action | payload | 触发 |
|--------|---------|------|
| `team_create` / `team_dissolve` | teamId, name, operatorId | 建组/解散 |
| `team_member_join` / `team_member_leave` | teamId, userId, operatorId | 拉人/退组（含被移除） |
| `team_grant_create` | teamId, entityType, entityId, permission, grantedBy | 授权/复活授权/改档 |
| `team_grant_revoke` | teamId, entityType, entityId, revokedBy, reason | 撤销授权 |

AuditLog 是审计**最终真源**（grant 行仅承载当前状态 + 可变历史），即使 grant 行异常丢失，审计链完整。

## §5 可见性合成规则

### 5.1 合成公式（v2.1 修订：组为主，部门维退出）

```
visible(entity, user) =
    scopeKind == 'all'                                          → true      // 财务/QC/后勤/管理员/超管，零影响
  ∨ 本人维（ownerId = user ∨ salesRepIds ∋ user）                 // v2.1：PL-2B 部门子树维退出
  ∨ TeamDataGrant ∃ (teamId ∈ activeTeams(user)                  // 小组维
                     ∧ entityType = 'relation'
                     ∧ entityId = entity.id
                     ∧ revokedAt IS NULL
                     ∧ team.deletedAt IS NULL)
```

**v2.1 口径变更说明**：

- **v2（旧）**：`部门维 ∪ 小组维`——同部门互见 + 组共享，部门子树是主隔离维度
- **v2.1（新）**：`本人维 ∪ 小组维`——自己的数据 + 所加入组的共享数据（多组并集）
- **变更后果**：
  1. 普通业务员不再看到本部门同事未共享的客户（外贸客户档案有提成归属敏感性，同部门互见是过度授权）；
  2. 销售主管的管理视野 = 所加入的所有组的并集（组驱动），非部门子树——要管谁就把主管拉进对应的组；
  3. 部门保留两个用途：组织架构树目录展示 + DR-007 审批人解析（`resolveReviewerByDepartment`），**不再进 scopeWhere 计算**；
  4. `salesRepIds ∋ user` 保留：业务员作为跟单协作者（salesRep 数组含自己）仍可见，属于本人维的自然延伸。
- **迁移注意**：`relationServiceV2.buildScopeWhere` / `buildWriteScopeWhere` 中 PL-2B 部门子树逻辑（`collectSubtreeDeptIds` 消费）切为本人维；其他域若存在部门维 scope 需同步对齐口径；既有测试需回归修订。

**并集不是交集**：本人维与小组维取并——用户看到自己的客户 + 各组被共享进来的客户，多组之间也是并集融合。

### 5.2 归属解析时机（v2 关键修订）

**每请求解析，不进 JWT claims**（JWT 是 7 天 cookie，缓进去退组后最长 7 天仍可见，违反 T-03 即时失效）：

- `activeTeams(user)` = `TeamMember WHERE userId = me AND leftAt IS NULL`（`@@index([userId])` 已存在，毫秒级单查）；
- 进程内可选 60s TTL 缓存（key = userId），失效窗口 ≤ 60s，验收线 T-03 以 60s 为上界；
- 授权 ID 集合（grantedEntityIds）同策略：按 (userTeams × activeGrants) 单查取回，进 `IN` 子句。

### 5.3 子实体派生可见性

Relation 被共享后，其子树可见性派生规则：

| 子实体 | 派生规则 | 前置 |
|--------|---------|------|
| 订单 Order | `customerRelationId ∈ grantedRelationIds` → 详情/列表可见 | Phase 3（订单列表行级过滤上线后接入；当前订单无行级过滤，全员可见，共享对其为无害超集） |
| 报价 Quotation | 同上（按 relation 关联） | Phase 3 |
| 跟进记录 FollowUpRecord | 随 Relation 详情可见；**写入**按 permission 档位门禁（§6.2） | Phase 2 |
| 附件/文档 | 随宿主实体可见性 | Phase 2 |

派生规则的语义：**共享客户 = 共享其全部业务上下文**，不存在「共享档案但藏起订单」的割裂态。

### 5.4 失效优先级（多重状态叠加时的裁决序）

```
实体软删（deletedAt ≠ null）        → 不可见（一票否决，最高优先级）
用户退组（leftAt ≠ null）            → 该组授权对其失效
授权撤销（revokedAt ≠ null）         → 该授权失效
组解散（team.deletedAt ≠ null）      → 该组全部授权失效
账号停用                             → 一切失效
```

任何一层失效立即生效（下次查询即不可见），不做宽限期。

## §6 权限矩阵

### 6.1 角色 × 小组能力矩阵

**核心不变量（v2 修订 4）**：**对实体有行级写权限者，才可共享/撤销该实体的授权**。授权是写相邻动作——你不能决定别人看到一个你无权修改的东西。该不变量复用既有写权限校验（`buildScopeWhere` 的写侧），无需新口径。

| 能力 | 业务员 | 销售主管 | 组长 | 财务 | QC/后勤 | 管理员/超管 |
|------|--------|---------|------|------|---------|------------|
| 创建/解散小组 | ❌ | ✅ | ❌ | ❌ | ❌ | ✅ |
| 拉人/移除组员 | ❌ | ✅ | ✅（本组） | ❌ | ❌ | ✅ |
| 设置组长 | ❌ | ✅ | ❌ | ❌ | ❌ | ✅ |
| 授权数据给组 | ❌ | ✅（对有写权限的实体） | ✅（对有写权限的实体） | ❌ | ❌ | ✅ |
| 撤销授权 | ❌ | ✅（同上） | ✅（本组） | ❌ | ❌ | ✅ |
| 见组内共享数据 | ✅（所在组） | ✅（所在组） | ✅（所在组） | ✅（all 全量） | ✅（all 全量） | ✅（all 全量） |

注：组长授权仍受双重门禁——「是本组组长」∧「对该实体有写权限」。组长不是角色，是身份叠加（不新增系统角色，DR-041 容器不动）。

### 6.2 共享数据的读写分级

| 数据操作 | permission='read' | permission='read+followup' |
|---------|-------------------|---------------------------|
| 查看客户档案详情 | ✅ | ✅ |
| 查看该客户订单/报价/跟进历史（派生） | ✅ | ✅ |
| 添加跟进记录（FollowUpRecord） | ❌ 403 | ✅ |
| 修改档案本体字段（信用等级/付款条款等） | ❌ 403 | ❌ 403（永远只归属部门可写） |
| 以该客户名义新建订单/报价 | ❌ 403 | ❌ 403（须归属部门成员操作） |
| 导出/下载附件 | ✅ | ✅ |

**分级理由**：外贸协作真实场景是「欧洲组同事帮着跟进 H&M 询价」——跟进记录可写足够覆盖；档案本体（信用/条款/额度）多手共改是审计灾难，收敛归属部门单写。

### 6.3 权限守卫顺序

```
模块 scope（DR-041 既有）→ 行级数据范围（PL-2B 部门维 ∪ 小组维）→ 档位门禁（read / read+followup / 本体写）
```

三层守卫逐层收窄，任何一层拒绝即 403，错误码区分：`MODULE_FORBIDDEN` / `SCOPE_BLOCKED` / `GRANT_PERMISSION_BLOCKED`。

## §7 API 契约

复用既有 `/api/hr/teams` CRUD（已存在），新增授权子资源与查询端点：

| 方法 | 路径 | 说明 | 权限守卫 |
|------|------|------|---------|
| GET | `/api/hr/teams/mine` | 当前用户所在组列表（含 leaderId/成员数/授权数） | 任何登录用户 |
| GET | `/api/hr/teams/:id` | 组详情（成员/授权/审计摘要） | 本组成员 ∨ 主管 ∨ admin |
| GET | `/api/hr/teams/:id/grants` | 组内授权列表（含已撤销，审计视图，分页） | 组长/主管/admin |
| POST | `/api/hr/teams/:id/grants` | 批量授权 `{ items: [{entityType, entityId, permission}] }` | §6.1（双重门禁） |
| PATCH | `/api/hr/teams/:id/grants/:grantId` | 改档 `{ permission }` | §6.1 |
| PATCH | `/api/hr/teams/:id/grants/:grantId/revoke` | 软撤销 `{ reason }` | §6.1 |
| GET | `/api/v1/relations/:id/team-shares` | 反查该客户共享给了哪些组（详情页 chips） | 该数据可见者 |
| POST | `/api/v1/relations/:id/team-shares` | 详情页就地共享（等价 grants 批量接口的便捷封装） | 对该 relation 有写权限者 |

契约细则：
- **幂等**：`@@unique([teamId, entityType, entityId])` 下，重复授权 = 更新 permission；撤销后再授权 = 复活原行；
- **错误码**：`TEAM_NOT_FOUND`(404) / `TEAM_DISSOLVED`(409，向已解散组建授权) / `ENTITY_NOT_FOUND`(404，被共享实体不存在) / `GRANT_SCOPE_BLOCKED`(403，无该实体写权限) / `GRANT_PERMISSION_BLOCKED`(403，档位不足)；
- **事务性**：解散组为单事务（§9.2）；批量授权部分失败整批回滚（不做部分成功，避免半授权态）；
- 所有变更写 AuditLog（§4.3）。

## §8 UI 呈现设计（v2 细化）

### 8.1 呈现总原则：不按组建视图，按业务对象统一列表

N 个组的内容**不分块**，全部汇入既有业务列表，只带来源标记。防混乱三支柱：

1. 主工作流永远是业务对象（今天处理哪些客户/订单）——组的数量不改变主轴，列表只变长一点；
2. 来源徽章是**弱信息**（小尺寸雾化 tint，BDS 范式），不关心的人可忽略，关心的人用筛选器精确定位；
3. 进组数量上限靠制度不靠界面：建组需主管/管理员权限（§6.1），组织泛滥在源头被控。

### 8.2 列表页（以客户列表为例）

```
客户列表（统一排序：最近互动/状态/金额——排序键与组无关）
┌────────────────────────────────────────────┐
│ H&M        [我的]          最近互动 2h前    │
│ ZARA       [波兰成衣组·共享] 最近互动 1d前  │
│ 优衣库     [日本面料组·共享] 最近互动 3d前  │
│ 国富纺织   [我的]          最近互动 5d前    │
└────────────────────────────────────────────┘
     筛选器：[全部] [我的] [波兰成衣组] [日本面料组]
```

- 徽章规则（v2.1）：归属徽章改为「我的」（本人维命中）；组共享徽章显示来源组名；两者同时命中只显示「我的」（主归属优先，不叠双徽章）；
- 筛选器默认值 = 用户个人偏好（记住上次选择，符合「系统设置管个人偏好」分层）；首次默认「全部」——组数据本就是有意共享给该用户的协作内容，不存在淹没问题（v2.1 口径：本人∪组 = 该用户完整工作面）；
- all-scope 用户（财务/QC/后勤/admin）：无徽章、无组筛选器（他们看全量，组维度对其透明）。

### 8.3 详情页

```
H&M 客户详情
┌────────────────────────────────────────────┐
│ H&M  [本部门]   共享至: 欧洲组 ✕  H&M组 ✕  │  ← chips；✕ 对有权限者可就地移除
│────────────────────────────────────────────│
```

- chips hover 显示授权人/时间/档位；
- 有写权限者（主管/归属部门/组长）可就地添加共享，不跳 AdminPanel；
- **优雅失效态**：会话中授权被撤销 → 下次操作返回 404/403 → 前端转译为「该数据已取消共享」提示页，不裸抛错误。

### 8.4 组主页（补充视图，非主入口）

侧边栏「我的小组」→ 组详情页：
- 成员区（组长标识/移除/退组按钮）+ 授权区（按 entityType 分栏、批量勾选客户）；
- 组长用此页管理；普通组员日常**完全不经过**这里（数据自己流入主列表）；
- 解散组二次确认（BdsDialog：明确提示「全部授权将失效，组员将立即失去共享数据可见性」）。

### 8.5 小组管理入口（v2.1：归位 HRManager 人事管理）

**权责划分原则**：AdminPanel 管"平台怎么运转"（软件层治理：账号/角色/工具权限/平台规则/公司主体/知识库 ACL——换家公司要重配的东西）；HRManager 管"本公司怎么组织"（组织人事：部门/小组/项目/任务/员工档案/考勤薪资绩效培训——描述本公司组织形态）。

- **HRManager·小组管理**（从 AdminPanel 迁入，v2.1 唯一管理真源）：组列表（组名/组长/成员数/生效授权数/状态）+ 建组表单（bds-select 选组长、关联部门可选、多选成员）+ 组编辑（改名/换组长/换关联部门，调既有 PATCH）+ 组详情（成员管理 + 授权管理 + 审计视图 + 解散，复用 8.4 组件）；
- AdminPanel 移除小组管理 Tab（后端 `/api/hr/teams*` 零改动，本就挂 hr 域——UI 迁移即前后端语义对齐）；
- HRManager·组织架构树：部门树 + 人员编制 + 该部门成员参与的小组（只读目录展示，建组/管组统一走小组管理入口；跨部门组在树顶部"跨部门小组"区展示，不再叫"孤儿团队"）；
- **项目/任务挂靠**（v2.1）：项目/任务从"编制团队"迁移挂靠到小组——一个小组 = 数据共享 + 项目任务 + 协作跟进的完整业务单元（如「波兰成衣组」既有共享客户又有项目任务）；"编制团队"概念消除。

### 8.6 Dashboard 视角聚焦器（v2.1 新增）

Dashboard 顶部的组选择器定位为**经营视角过滤器**，不是权限切换：

- **权限层（数据获取）永远融合**：用户视野 = 本人 ∪ 所在全部组（并集），无任何"切换"概念；
- **展示层可选聚焦**：默认「全部」显示融合全景概况；点选某组 → 看板聚焦该组的经营切片（该组关联客户/订单/跟单/业绩统计）；
- **角色语义**：老板/超管可逐组巡检（组选择器含全公司所有组）；销售主管看自己所加入各组的健康度；all-scope 角色（财务/QC）无聚焦器或可选全量；
- **实现要点**：聚焦 = Dashboard 聚合查询的 `teamId` 过滤参数（组关联实体集 = TeamDataGrant 生效授权实体），不动任何权限接口。

## §9 边界、竞态与失效语义

### 9.1 边界场景裁决表

| # | 场景 | 裁决 | 理由 |
|---|------|------|------|
| B-01 | 实体软删但授权生效中 | 不可见（deletedAt 一票否决） | §5.4 失效优先级 |
| B-02 | 实体归属部门迁移（departmentId 变更）后原授权 | **继续生效**（授权挂在实体上，非部门上） | 快照语义；换部门不该静默撕毁既有协作约定 |
| B-03 | 组长退组（leader 本人 leftAt） | 组继续运作（授权与成员不受影响）；UI 提示「组长空缺」 | 组长是管理入口非运作前提 |
| B-04 | 组内零成员但授权生效 | 无害空转（可见性要求 user ∈ team，无人满足） | 无需清理任务 |
| B-05 | 授权人自身权限被收（后来无该实体写权限） | 既有授权**不自动回收**（避免权限变更引发大面积静默失效）；由主管在审计视图人工清理 | 显式优于隐式；AuditLog 提供清理线索 |
| B-06 | 同一用户被同一实体经多组可见 | 徽章只显示一条（取第一个命中的组，字典序） | 去重呈现 |

### 9.2 解散组事务（竞态核心防护）

```
POST /api/hr/teams/:id/dissolve 事务体：
1. 校验 team 存在 ∧ deletedAt IS NULL（防重复解散）
2. UPDATE TeamDataGrant SET revokedAt=now, revokedBy=operator,
        revokeReason='team dissolved'
   WHERE teamId=:id AND revokedAt IS NULL
3. UPDATE Team SET deletedAt=now
4. AuditLog(team_dissolve)
```

竞态裁决：
- 解散进行中收到新授权请求 → 步骤 1 校验失败或步骤 2/3 与授权事务的行锁互斥，后到者见 `TEAM_DISSOLVED` 409；
- 解散 vs 撤销并发 → 同一行 revokedAt，后写覆盖先写（结果等价：已撤销），AuditLog 各留一条；
- 进程崩溃于事务中 → 整体回滚，组回到未解散态，可重试（幂等）。

### 9.3 读侧竞态（授权撤销 vs 用户正在浏览）

- 撤销后用户已打开的详情页：下次任何 API 调用（含轮询）返回 403/404 → §8.3 优雅失效态；
- 不做服务端推送（SSE 通知撤销）——成本不成比例，拉取失效足够（60s 缓存上界内）。

## §10 性能与规模

| 关注点 | 量级评估 | 对策 |
|--------|---------|------|
| activeTeams 查询 | 用户 ∈ 组数（预期 ≤5），单查 `TeamMember(userId)` 有索引 | 每请求直查，毫秒级 |
| grantedEntityIds 集合 | 组数 × 组均授权数（中型外贸公司客户总量百~千级） | `IN` 子句承载；预期 ≤2000 ID，Postgres 无压力 |
| 列表查询 | scopeWhere 增加一个 OR 分支 `{ id: { in: grantedIds } }` | 与既有 PL-2B OR 组合同构，复用索引 |
| 缓存 | 归属/授权 ID 集 60s TTL 进程内缓存 | 失效上界 60s，验收线 T-03 |
| 规模升级路径 | 授权总量 >10k 或成员结构复杂化 | 预研 EXISTS 子查询/raw SQL（本期不做，记录演进方向） |

验收性能线：授权 2000 条规模下，客户列表 P95 < 500ms（与改造前基线对比劣化 < 50ms）。
