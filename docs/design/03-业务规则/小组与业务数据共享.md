# 小组与业务数据共享（DR-042）

> **决策提议编号**：DR-042（自定义小组 + 业务数据受控共享）
> **关联决策**：DR-041（7+1 宽泛容器角色）/ PL-2B（同部门互相可见，跨部门隔离）/ DR-007（审批人按部门解析）
> **落地状态**：❌ 设计阶段（Team/TeamMember 模型与 HR CRUD 已存在但为空壳，业务数据共享链路未实现）
> **核心意图**（项目决策登记原文）：「角色权限通过 departmentId 实现分组隔离，**支持按品牌客户、市场或业务类型自定义小组**」

## §2 概念定位：部门 vs 小组

| 维度 | 部门 Department | 小组 Team |
|------|---------------|-----------|
| 本质 | 行政组织架构 | 业务分组单元 |
| 组建逻辑 | 稳定汇报线（销售部/财务部/总经办） | 按品牌客户/市场/业务类型自由组建（如「优衣库品牌组」「欧洲市场组」） |
| 成员规则 | 单一归属（`UserAccount.primaryDeptId` 一对一） | 多对多（一人可同时进 N 个组，TeamMember） |
| 跨部门 | 否，树形封闭 | 是，`Team.departmentId` 可空 = 天然跨部门 |
| 消费场景 | DR-007 审批人解析 / HR 编制 / 汇报线 | 业务数据共享：组内可见彼此的客户/订单/报价 |
| 生命周期 | 长期稳定（低频变更） | 高频（项目启动建组、结束解散） |
| 维护者 | 管理员 | 销售主管/管理员（随业务调整） |

**铁律**：小组**不参与**审批人解析（那是 DR-007 部门 `headId` 的职责）；小组**只影响数据可见性**。两条链路正交解耦，避免「一条数据到底跟部门走还是跟组走」的语义混乱。

## §3 建模取舍

### 3.1 方案 A：业务实体直接归属（挂 teamId）

在 Relation/Order/Quotation 上直接加 `teamId String?` 字段。

```
Relation.teamId ──FK──▶ Team
```

| 优点 | 缺点 |
|------|------|
| 模型简单，查询快（单字段过滤） | **单值归属**：一条数据只能属于一个组；「H&M 的订单」无法同时属于「欧洲市场组」+「H&M 品牌组」 |
| 无新增表 | 组解散时数据要迁移 teamId（脏活） |
| 语义直观 | 与部门归属并存语义混乱：数据的组织归属出现两个真源 |
| | 「按品牌客户/市场/业务类型」三种切法天然交叉，单值装不下 |

### 3.2 方案 B：共享授权表（TeamDataGrant）✅ 采用

数据本体不动（归属仍是部门链路），新增授权表表达「这个实体共享给哪个组看」。

```
TeamDataGrant
├─ teamId      FK Team
├─ entityType  'relation' | 'order' | 'quotation'（可扩展）
├─ entityId    被共享实体 id
├─ permission  'read' | 'read+followup'（写权限分级，§6）
└─ grantedBy / grantedAt / revokedAt（审计链）
```

| 优点 | 缺点 |
|------|------|
| **多对多**：一个客户可同时授权给多个组 | 多一张表，可见性查询要 OR 子查询 |
| 数据本体不动：部门链路（DR-007 审批/归属）零影响 | 授权操作比「勾个字段」多一步 |
| 组解散 = 撤销授权，数据无感回归部门范围 | |
| 纯增量：Team/TeamMember 已有，加表无迁移风险 | |
| 授权自带审计链（谁授权/何时/撤销） | |

### 3.3 决策

**采用方案 B（TeamDataGrant）**，核心理由：

1. **业务本质是多维交叉**——「按品牌客户、市场或业务类型」三种切组方式天然重叠，单值 teamId 装不下；
2. **正交解耦**——数据组织归属唯一真源仍是部门（DR-007 审批链不被污染），小组是纯粹的「共享视图」；
3. **生命周期安全**——小组是高频生灭的业务单元，授权撤销即解散，业务数据永不迁移。

**明确不做**（防过度设计）：
- 不做组的自动规则归集（rule-based grant，如「欧洲客户自动进欧洲组」）——留作后期演进方向记录，首期手动授权；
- 不做组内层级（组长→副组长）；只保留 `Team.leaderId` 单一组长 + `TeamMember.role`（member/leader）既有字段。

## §4 数据模型设计

### 4.1 新增：TeamDataGrant（Prisma）

```prisma
/// DR-042 小组数据共享授权：业务实体 × 小组 多对多受控共享。
/// 铁律：数据本体组织归属不变（部门链路），本表仅表达「共享视图」。
model TeamDataGrant {
  id          String    @id
  teamId      String
  entityType  String    // 'relation' | 'order' | 'quotation'（enum 起步三值，按域扩展）
  entityId    String    // 被共享实体 id（快照引用，不强 FK——与 Order.customerRelationId 同范式）
  permission  String    @default("read+followup") // 'read'（纯只读）| 'read+followup'（可加跟进记录）
  grantedBy   String    // 授权人 UserAccount.id
  grantedAt   DateTime  @default(now())
  revokedAt   DateTime? // 软撤销（null=生效中）；保留行以留审计痕迹
  revokeReason String?

  team Team @relation(fields: [teamId], references: [id], onDelete: Cascade)

  @@unique([teamId, entityType, entityId]) // 同一实体对同一组只有一条有效授权（幂等）
  @@index([entityType, entityId])          // 反查：这条数据共享给了哪些组
  @@index([teamId, revokedAt])             // 正查：这个组能看到哪些数据
}
```

设计要点：
- **软撤销不物理删**：授权历史是审计链（谁在何时把客户共享给过哪个组），`revokedAt` 置位即失效；
- **entityId 不强 FK**：与 `Order.customerRelationId` 快照引用同范式（Relation 可独立归档，不级联）；
- **permission 只有两档**：`read` / `read+followup`。**没有 `write` 档**——档案本体（客户资料/订单字段）永远只有归属部门可写，组内共享只读 + 跟进记录可写（§6 详述），规避多人共改一条档案的数据风险。

### 4.2 复用既有（零改动）

- `Team`（schema.prisma:1198）：`leaderId` 即组长；`departmentId` 可空保持跨部门语义；
- `TeamMember`（schema.prisma:1219）：`role`（member/leader）+ `leftAt` 退出标记；
- `DataScopeRule`（rolePermissionMatrix.ts:304）：启用既有 `{ kind: 'team' }` 分支。

### 4.3 DataScopeRule 消费方扩展

行级过滤器合成逻辑（伪码）：

```
visible(entity, user) =
    scopeKind == 'all'                                    → true
  ∨ entity.ownerDeptId == user.primaryDeptId              // PL-2B 既有部门维
  ∨ TeamDataGrant ∃ (teamId ∈ userTeams(且未退出/未撤销)
                     ∧ entityType = entity.type
                     ∧ entityId = entity.id
                     ∧ revokedAt = null)
```

用户所在组集合 `userTeams` = TeamMember 中 `leftAt IS NULL` 的 teamId 集合（缓存于 JWT claims 或会话态，避免每请求查库）。

## §5 可见性合成规则

用户可见数据 = **自己创建的** ∪ **同部门（PL-2B 既有）** ∪ **所在小组被授权的**。

规则细节：

1. **并集不是交集**：部门维与小组维取并——组员看得到自己部门的全部客户 + 其他部门被共享进组的客户；
2. **组解散/退组即时生效**：TeamMember.leftAt 置位或 Grant.revokedAt 置位后，下一次查询即不可见（无缓存脏读窗口，会话级缓存 TTL ≤ 60s）；
3. **写权限与可见性分离**：看得见 ≠ 改得了（§6）；
4. **all 角色不受影响**：财务/QC/后勤/管理员/超管 scope='all'，小组维是纯增量放大，对他们透明。

## §6 权限矩阵

### 6.1 角色 × 小组能力矩阵

| 能力 | 业务员 | 销售主管 | 组长 | 财务 | QC/后勤 | 管理员/超管 |
|------|--------|---------|------|------|---------|------------|
| 创建/解散小组 | ❌ | ✅（本部门关联组） | ❌ | ❌ | ❌ | ✅ |
| 拉人/移除组员 | ❌ | ✅（本部门关联组） | ✅（本组） | ❌ | ❌ | ✅ |
| 设置组长 | ❌ | ✅ | ❌ | ❌ | ❌ | ✅ |
| 授权数据给组 | ❌ | ✅（本部门归属的数据） | ✅（仅跟进级，不能授纯读外的档位变更） | ❌ | ❌ | ✅ |
| 撤销授权 | ❌ | ✅ | ✅（本组） | ❌ | ❌ | ✅ |
| 见组内共享数据 | ✅（所在组） | ✅（所在组） | ✅（所在组） | ✅（all 全量） | ✅（all 全量） | ✅（all 全量） |

### 6.2 共享数据的读写分级

| 数据操作 | permission='read' | permission='read+followup' |
|---------|-------------------|---------------------------|
| 查看客户档案/订单/报价详情 | ✅ | ✅ |
| 添加跟进记录（FollowUpRecord） | ❌ | ✅ |
| 修改档案本体字段 | ❌ | ❌（永远只归属部门可写） |
| 新建订单/报价挂到共享客户名下 | ❌ | ❌（须归属部门成员操作） |
| 导出/下载附件 | ✅ | ✅ |

**分级理由**：外贸协作的真实场景是「欧洲组的同事帮着跟进 H&M 询价」——跟进记录可写足够覆盖；档案本体（信用等级/收款条款等敏感字段）多手共改是审计灾难，收敛为归属部门单写。

### 6.3 与 DR-041 容器角色的挂接

小组能力**不新增系统角色**，全部通过既有 8 容器角色 + 组长身份（TeamMember.role）合成：
- 组长不是角色，是「身份叠加」：任何角色（默认业务员）成为组长后获得 §6.1 组长列能力；
- 权限守卫顺序：模块 scope（DR-041）→ 数据范围（PL-2B + 本设计小组维）。

## §7 API 设计

复用既有 `/api/hr/teams` CRUD（已存在），新增授权子资源：

| 方法 | 路径 | 说明 | 权限守卫 |
|------|------|------|---------|
| GET | `/api/hr/teams/:id/grants` | 组内授权列表（含已撤销，审计视图） | 组长/主管/admin |
| POST | `/api/hr/teams/:id/grants` | 批量授权 `{ items: [{entityType, entityId, permission}] }` | §6.1 授权行 |
| PATCH | `/api/hr/teams/:id/grants/:grantId/revoke` | 软撤销 `{ reason }` | §6.1 撤销行 |
| GET | `/api/hr/teams/mine` | 当前用户所在组（会话态缓存源） | 任何登录用户 |
| GET | `/api/v1/relations/:id/team-shares` | 反查该客户共享给了哪些组（详情页展示） | 数据可见者 |

契约要点：
- 授权幂等：`@@unique([teamId, entityType, entityId])` 重复授权 = 更新 permission 而非报错；
- 撤销后再授权 = 复活原行（revokedAt 置 null），保留完整历史；
- 所有授权/撤销写 AuditLog（action: `team_grant_create` / `team_grant_revoke`）。

## §8 UI 设计要点

1. **AdminPanel 新增「小组管理」Tab**（与用户/角色 Tab 并列）：
   - 组列表（组名/组长/成员数/授权数/状态）+ 建组表单（BDS 范式：bds-select 选组长、多选成员）；
   - 组详情：成员管理区 + 授权管理区（按 entityType 分栏，支持批量勾选客户授权）；
   - 解散组二次确认（BdsDialog，说明授权将全部失效）。
2. **业务单据详情页共享标识**：
   - Relation 详情页头部：共享组 chips（如「欧洲市场组 ×」「H&M 品牌组 ×」），hover 显示授权人与时间；
   - 主管/组长可就地添加/移除共享（不跳 AdminPanel）。
3. **列表页可见性无感**：小组维共享数据自然混入列表（带共享图标 badge 区分「本部门」vs「组共享」），不单独开视图。

## §9 验收用例

### 9.1 组生命周期用例

| 编号 | 场景 | 前置 | 步骤 | 期望 | 失败路径 |
|------|------|------|------|------|---------|
| T-01 | 建组 | 销售主管登录 | AdminPanel→小组管理→建组「欧洲市场组」，拉入 2 名跨部门业务员，设组长 | 组创建成功，组员立即可见该组 | 无权限建组 → 403 |
| T-02 | 一人多组 | 用户已在「H&M 品牌组」 | 加入「欧洲市场组」 | 用户同时属 2 组，两组合并可见 | — |
| T-03 | 退组 | 组员在组 | 组长移除该组员 | 下一次列表查询组内共享数据即消失 | 移除后仍可见（缓存脏读>60s）= 缺陷 |
| T-04 | 解散组 | 组存在且有授权 | 管理员解散 | 全部授权 revokedAt 置位；组员数据回归纯部门范围；组软删（deletedAt） | 数据仍可见 = 缺陷 |

### 9.2 授权与可见性用例

| 编号 | 场景 | 前置 | 步骤 | 期望 | 失败路径 |
|------|------|------|------|------|---------|
| T-05 | 单组授权 | 客户 H&M 归属销售部；采购部业务员在「欧洲组」 | 主管将 H&M 授权给欧洲组 | 采购部组员列表出现 H&M（带共享 badge），销售部成员不受影响 | 采购组员看不到 = 缺陷 |
| T-06 | 多组交叉授权 | H&M 已授权「欧洲组」 | 再授权「H&M 品牌组」 | 两组组员均可见；授权行 2 条 | 第二次授权报唯一冲突（未做幂等升级）= 缺陷 |
| T-07 | 部门维 ∪ 组维 | 组员本部门有客户 A；组内共享客户 B | 查看列表 | A、B 均可见 | 交集逻辑导致 A 被滤掉 = 缺陷 |
| T-08 | 撤销授权 | T-05 生效中 | 主管撤销 H&M 对欧洲组的授权 | 组员下次查询 H&M 消失；审计日志有 team_grant_revoke 记录 | 数据仍可见 = 缺陷 |
| T-09 | all 角色不受影响 | 财务登录 | 查看客户列表 | 全量可见（无组过滤干扰），与改造前一致 | 财务可见性变化 = 回归缺陷 |

### 9.3 读写分级用例

| 编号 | 场景 | 前置 | 步骤 | 期望 | 失败路径 |
|------|------|------|------|------|---------|
| T-10 | read+followup 可跟进 | T-05 生效，permission=read+followup | 采购组员在 H&M 详情页添加跟进记录 | 创建成功，记录作者=采购组员 | 403 = 缺陷（档位未生效） |
| T-11 | 档案本体不可写 | T-10 同前置 | 采购组员修改 H&M 信用等级字段 | 403（组共享不开放本体写） | 写成功 = 越权缺陷（严重） |
| T-12 | read 档跟进不可写 | 授权 permission=read | 组员添加跟进记录 | 403 | — |
| T-13 | 共享客户不可下单 | T-10 同前置 | 采购组员以 H&M 名义新建订单 | 403（订单须归属部门成员操作） | 下单成功 = 越权缺陷 |

### 9.4 权限矩阵回归用例

| 编号 | 场景 | 步骤 | 期望 |
|------|------|------|------|
| T-14 | 业务员不能建组 | 业务员调 POST /api/hr/teams | 403 |
| T-15 | 组长只能管本组 | 组长 A 对组 B 拉人/授权 | 403 |
| T-16 | 授权范围越界 | 销售主管授权非本部门归属的数据给组 | 403（只能授本部门归属数据） |
| T-17 | 审计完整性 | T-05+T-08 后查 AuditLog | create/revoke 各 1 条，含 actor/entity/team/reason |
